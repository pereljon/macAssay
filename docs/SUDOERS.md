# Sudo rules

This file describes the sudoers file that macAssay installs: each command it allows, what the command reads, why it cannot change the Mac, and which check uses it. It also covers the `Defaults` line, the grant line, and the installer. It does not weigh whether to install the file; [README.md](../README.md#privileged-checks-optional) covers that trade-off.

The file `/etc/sudoers.d/macassay` lets one account run a fixed list of read-only commands as root, without a password. Each rule names a stock macOS program by its full path, with exact arguments. sudo refuses any other program, any other argument, and any extra argument. The function `gen_rules` in `macassay` writes the file, and `./macassay --print-sudoers` prints it without installing anything.

## Example

This example is the output of `gen_rules` for a test Mac with Apple silicon, where `alice` is the account that runs the audit. The Mac has one other account, `bob`, and one other file in `/etc/sudoers.d`, `extra_rules`. The fixture tests in `dev/test.sh` check that this block matches `gen_rules`.

<!-- sudoers-example: dev/test.sh compares this block with gen_rules output, from its second line on. -->
```text
# macassay read-only rules for alice, generated by macassay VERSION.
# Undo: sudo rm /etc/sudoers.d/macassay
Cmnd_Alias MACASSAY = \
    /usr/sbin/lsof -nP -iTCP -sTCP\:LISTEN, \
    /usr/sbin/lsof -nP -d txt -Fpn, \
    /sbin/pfctl -s info, \
    /sbin/pfctl -s rules, \
    /usr/bin/sfltool dumpbtm, \
    /usr/bin/du -h -d 1 -x /Users, \
    /usr/bin/du -sh -x /Library /Applications /opt /private/var, \
    /usr/bin/profiles list -type configuration, \
    /usr/bin/bputil -d, \
    /bin/cat /etc/sudoers, \
    /bin/cat /etc/sudoers.d/extra_rules, \
    /bin/cat /etc/sudoers.d/macassay, \
    /bin/ls -ln /var/at/tabs, \
    /usr/bin/ssh-keygen -l -f /var/root/.ssh/authorized_keys, \
    /bin/ls -ln /var/root/Library/LaunchAgents, \
    /bin/ls -lnd /var/root/.zshrc /var/root/.zprofile /var/root/.zshenv /var/root/.zlogin /var/root/.bashrc /var/root/.bash_profile /var/root/.profile, \
    /usr/bin/ssh-keygen -l -f /Users/bob/.ssh/authorized_keys, \
    /bin/ls -ln /Users/bob/Library/LaunchAgents, \
    /bin/ls -lnd /Users/bob/.zshrc /Users/bob/.zprofile /Users/bob/.zshenv /Users/bob/.zlogin /Users/bob/.bashrc /Users/bob/.bash_profile /Users/bob/.profile
Defaults!MACASSAY always_set_home, !set_utmp
alice ALL = (root) NOPASSWD: MACASSAY
```

`Cmnd_Alias MACASSAY` names the list of commands, so that the `Defaults` line and the grant line can refer to it.

## Commands

The rule list depends on the Mac:

- `bputil -d` appears only on a Mac with Apple silicon.
- `/etc/sudoers.d/FILE` stands for each file in `/etc/sudoers.d`. The list always includes `macassay` itself, although the audit skips that file when it reads `/etc/sudoers.d`.
- `HOME` stands for the home folder of each other account: root (`/var/root`) and each local account with a user ID (UID) of 501 or above, except the account that runs the audit. That account reads its own files without sudo.

## How the rules stay read-only

These limits apply to every rule. Each one comes from `man sudoers` or from the code.

- A rule with arguments matches only those arguments (`man sudoers`). A command with an extra, missing, or changed argument does not match, and sudo refuses it.
- No rule argument holds a wildcard such as `*`. In sudoers, `*` in an argument also matches spaces and slashes. Test F2 in `dev/test.sh` checks for it.
- No rule allows a shell, an interpreter, an editor, or `sqlite3`. A program that can run other code would turn a read rule into a root shell. Test F2 checks this too.
- sudo reads `:` as a separator, so the `lsof` rule escapes it as `\:`.
- `gen_rules` skips an account, home folder, or `sudoers.d` file name that could change the meaning of a rule, and prints a warning. Test F3 covers hostile names. The checks are:
  - An account name must match `^[A-Za-z0-9_][A-Za-z0-9_.-]*$`.
  - A home folder must be `/var/root` for root, or `/Users/NAME` for other accounts.
  - A `sudoers.d` file name must match `^[A-Za-z0-9_-]+$`. sudo ignores a file whose name has a dot.
  - The granted account must be a regular account, with a UID of 501 or above. Its name must not be all capitals, because sudoers reads such a name as an alias, and `ALL` as every user.
- The audit runs each command through the function `priv`, as `sudo -n -k COMMAND`. `-n` stops sudo from asking for a password. `-k` makes sudo ignore a cached password, so only a rule without a password lets the command run. Without the file, `priv` makes no sudo call and records a skip.

## The Defaults line

`Defaults!MACASSAY always_set_home, !set_utmp` changes two sudo settings, for the macassay commands only.

- `always_set_home` sets `HOME` to root's home folder. The macOS default sudo policy keeps the caller's `HOME`, so without this setting a command run as root would read the user's home folder through `HOME`.
- `!set_utmp` stops sudo from writing a login record for each command. sudo 1.9.14 and later runs each command in a new pseudo-terminal, and with `set_utmp` on, it records each one as a login.
- `use_pty` stays on. It stops a command from typing input into the user's terminal, and several of the commands read untrusted text.

The design and the tests for `!set_utmp` are in `dev/features/fixes-1.3.2.md`.

## The grant line

`alice ALL = (root) NOPASSWD: MACASSAY` lets the account `alice`, on any host, run the MACASSAY commands as root, without a password. It grants nothing else: no other command, and no other target account.

## How the installer works

`sudo ./macassay --install-sudoers` writes the file. Without `=USER`, it grants the account that ran sudo. The function `install_mode` takes these steps:

1. Refuse to run without root.
2. Run `visudo -c` on the current sudo configuration. If it fails, stop, so that the installer never adds to a broken configuration.
3. Write the rules to a temporary file, and check that file with `visudo -c -f`.
4. List every folder above each path that a rule names as an argument, up to `/`. Check, as the granted account, whether that account can write any of them. If it can, stop and name the folders. A folder the account can write would let it swap a file for a symlink to another file.
5. If an identical file is already installed, stop. If the installed file differs, print the differences and keep a copy of the old file.
6. Write the new file as `/etc/sudoers.d/.macassay.new`, owned by root:wheel with mode 0440, then rename it to `macassay`. sudo ignores a file whose name has a dot, so it never reads a half-written file.
7. Run `visudo -c` again. If it fails, put back the old file, or remove the new one. If sudo still fails, print a recovery command that removes the file through an administrator prompt, without sudo.
8. Run `pfctl -s info` as the granted account, through `sudo -n -k`, to check that the rule works. On failure, keep the file and print a warning: a later line in `/etc/sudoers` may override the rules.
9. Warn when `/etc/sudoers` has no `includedir` line for `/etc/sudoers.d`, because sudo then ignores the file.
10. Print the undo command.

For a remote Mac, `./macassay --host HOST --install-sudoers` runs the installer on that Mac and asks for its sudo password.

The audit also checks the installed file. A file in `/etc/sudoers.d` that the rules do not cover, such as one added after the install, gives finding `MA-ACCOUNTS-007`.

## Undo

Remove the file with `sudo rm /etc/sudoers.d/macassay`. The audit then skips the privileged checks and lists them under Limitations in the report.
